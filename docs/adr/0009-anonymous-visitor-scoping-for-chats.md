# Anonymous Visitor scoping for Chats, instead of accounts or client-side storage

Every Chat/Message lived in one shared SQLite file with no ownership concept at all — any visitor's browser could list, open, or delete any other visitor's chats (see `docs/adr/0006-sqlite-for-chat-and-vector-store-persistence.md`). Real accounts (login, password/OAuth, per-user rows) were ruled out as too much complexity for a personal single-owner project; client-side-only storage (localStorage/IndexedDB) was considered too, but would have meant rewriting the sidebar, search, and title-streaming to work without a server-side list at all, for no real gain over the option below.

We instead mint an opaque random id (`crypto.randomUUID()`) into an `httpOnly`, `SameSite=Lax`, one-year cookie on a browser's first request — via `proxy.ts`, ahead of every page and API route — and add a `visitor_id` column to `chats`, filtered on every read/write. No login, no password, nothing the visitor ever sees or manages. `data/app.db` was wiped rather than migrated: its pre-existing rows had no owner and were dev/test data, not real visitor content.

This intentionally does not give cross-device continuity (a visitor's history is tied to whichever browser/cookie started it) and does not protect a chat from anyone who can read the server's cookies or database directly — it only fixes cross-visitor exposure from the browser side, which was the actual problem. If cross-device sync or protection from the server operator is ever needed, this scoping will need to be replaced with real accounts.
