# Rewrite the retrieval query from the full conversation

Retrieval previously embedded the visitor's latest message verbatim as the query against the Vector store. This breaks down two ways: a Conversational turn whose latest message only makes sense in light of earlier turns (e.g. "and the second one?" carries no retrievable meaning alone, even though the conversation as a whole clearly does), and a visitor writing in a language other than English (Documents are always English, and embedding a non-English query against English Chunks scores poorly regardless of topical relevance).

We now derive a Retrieval query instead of using the latest message directly: whenever the Vector store is non-empty, we make an extra call to the same chat Model, sending it the full transcript with an instruction to rewrite the visitor's latest message as a standalone English question — resolving references to earlier turns and translating if needed — and embed that result. We skip the call only when the store is empty, since there's nothing to search; unlike an earlier version of this decision, we do **not** skip it on the first turn, since a non-English first message still needs translating before embedding.

Notable choices and their trade-offs:
- **A second sequential Model call per turn** (rewrite, then reply) adds latency before the reply can start streaming, now on every populated-store turn rather than just multi-turn ones. We accept this because Ragdrien is a low-traffic personal chatbot (per ADR 0003); revisit if this app ever serves higher traffic or needs faster time-to-first-token.
- **Reusing the same Model/config for rewriting and replying**, rather than a second independently-configurable model, avoids a new environment variable for a task we haven't shown needs a different (e.g. smaller/faster) model. Same premature-optimization reasoning as ADR 0003.
- **One combined instruction (resolve references + translate) in a single call**, rather than a separate language-detection step: asking the Model to translate is a no-op when the text is already English, so a dedicated detection call would add a third round-trip for no real benefit.
- **Hardcoding English as the translation target**, rather than a configurable target language, because Documents are permanently English by policy — this isn't a "revisit later" deferral like the other premature-optimization calls above, it reflects a fixed constraint of the corpus.
- **Not translating retrieved Chunks back into the visitor's language** before injecting them as grounding context — the reply is generated from the visitor's original-language messages plus English chunks, relying on the chat Model's own multilingual ability to reply in the visitor's language while grounded in English snippets, rather than a third Model call per turn.
- **Failing closed** when the rewrite call errors (propagating the error rather than silently falling back to the raw last message), for the same reason as ADR 0002: a silent fallback would be indistinguishable from a correctly-working turn from the outside, hiding a real operational problem behind a degraded reply.
- **Feeding the rewrite call the full uncapped transcript**, consistent with ADR 0003, rather than a capped window of recent turns.
